# E5 — Izolare RLS per organizație

**Data:** 2026-10-24  
**Stare:** PASS  
**Bază:** Mecanismul C din E4 — `lab_runtime` NOINHERIT, transaction pooler (port 6543)

## Întrebare

Mecanismul C (`SET LOCAL ROLE` + `set_config(local=true)` per tranzacție) asigură izolarea datelor între organizații atunci când RLS este activat pe tabelele modulelor?  
Ce se întâmplă dacă `set_config` este apelat cu `local=false` (session-level) în loc de `local=true`?

## Setup

RLS aplicat pe staging (via `labs/experiments/setup-rls-staging.mjs`):

```sql
ALTER TABLE lab_booking.services      ENABLE ROW LEVEL SECURITY;
ALTER TABLE lab_booking.appointments  ENABLE ROW LEVEL SECURITY;

CREATE POLICY org_isolation ON lab_booking.services
  USING ("organizationId" = current_setting('app.organization_id', true))
  WITH CHECK ("organizationId" = current_setting('app.organization_id', true));

CREATE POLICY org_isolation ON lab_booking.appointments
  USING ("organizationId" = current_setting('app.organization_id', true))

```

## E5-safe: mecanismul C cu `local=true`

### Mecanism

Per request, o singură tranzacție:

```typescript
await db.$transaction(async (tx) => {
  await tx.$executeRawUnsafe('SET LOCAL ROLE lab_booking_user');
  await tx.$executeRaw`SELECT set_config('app.organization_id', ${orgId}, true)`;
  // queries — RLS filtrează automat la orgId
});
```

Ambele `SET LOCAL` și `set_config(..., true)` sunt scoped la tranzacție. La COMMIT sau ROLLBACK, ambele revin automat.

### Rezultate

#### `/api/e5/safe?org=e4-org-alpha`

| Verificare | Valoare | Status |
|---|---|---|
| `settingBeforeTx` | `""` (empty string — prior tx a lăsat GUC-ul definit la sesiune cu `""`) | ✓ |
| `settingInsideTx` | `"e4-org-alpha"` | ✓ |
| `settingAfterTx` | `""` (revenit după COMMIT) | ✓ |
| `servicesReturned` | 2 (ambele servicii alpha) | ✓ |
| `crossOrgDataVisible` | `false` | ✓ |
| `isolationOk` | `true` | ✓ |
| Latență | 141 ms | — |

#### `/api/e5/safe?org=e4-org-beta`

| Verificare | Valoare | Status |
|---|---|---|
| `settingBeforeTx` | `""` | ✓ |
| `settingInsideTx` | `"e4-org-beta"` | ✓ |
| `settingAfterTx` | `""` (revenit după COMMIT) | ✓ |
| `servicesReturned` | 1 (singurul serviciu beta) | ✓ |
| `crossOrgDataVisible` | `false` | ✓ |
| `isolationOk` | `true` | ✓ |
| Latență | 204 ms | — |

### Observație: `""` vs `NULL` după revenire

Postgres returnează `""` (string gol) pentru un GUC custom (`app.organization_id`) după ce `set_config(local=true)` expiră la finalul tranzacției, nu `NULL`. Acest comportament este corect și **securizat identic** cu `NULL`:

- Politica RLS: `"organizationId" = current_setting('app.organization_id', true)`
- `current_setting('app.organization_id', true)` returnează `""` → condiția `organizationId = ''` nu corespunde niciunui rând → **0 rânduri vizibile**

Diferența `""` / `NULL` este semantică pentru cod-ul de verificare, nu pentru securitate.

## E5-unsafe: `set_config` cu `local=false` (session-level)

### Mecanism testat

```typescript
// NESIGUR: set_config fără local=true — setarea rămâne la nivel de sesiune
await tx.$executeRaw`SELECT set_config('app.organization_id', ${contaminantOrg}, false)`;
```

### Rezultate

| Verificare | Valoare | Concluzie |
|---|---|---|
| `settingAfterSet` | `"e4-org-beta"` (setat la sesiune) | — |
| `settingInsideNewTransaction` | `"e4-org-beta"` (sesiunea încă o vede) | **CONTAMINARE** |
| `settingAfterTransaction` | `"e4-org-beta"` (persistă după tx) | **CONTAMINARE** |
| `servicesVisibleWithoutExplicitOrg` | 1 (serviciul `e4-org-beta`) | **DATE SCURSE** |
| `contaminated` | `true` | ✓ confirmat |

**Risc confirmat:** `set_config(..., false)` în session pooler sau transaction pooler, pe o conexiune reutilizată, permite ca setarea organizației unui request să fie vizibilă requestului următor pe aceeași conexiune — dacă acel request uită să apeleze `set_config`.

---

## Concluzie

| Aspect | Rezultat |
|---|---|
| RLS izolează corect datele per org | ✓ — 2 servicii alpha, 1 beta, 0 cross-org |
| `set_config(local=true)` revine după tranzacție | ✓ — `""` sau `NULL` (ambele sigure) |
| `SET LOCAL ROLE` revine după tranzacție | ✓ (confirmat în E4/c/isolation) |
| `set_config(local=false)` este periculos | ✓ — contamination confirmat |

**Regulă obligatorie pentru mecanismul C:** `set_config('app.organization_id', orgId, true)` — parametrul `true` (is_local) este **mandatory**. Orice omisiune creează risc de scurgere de date între organizații pe conexiunile reutilizate ale transaction pooler-ului.

## E5-bench: overhead RLS + set_config

### Metodă

Endpoint minimal `/api/e5/bench?v=<variant>` — un singur `db.$transaction`:

- **`v=rls`** — `SET LOCAL ROLE lab_booking_user` + `set_config('app.organization_id', 'e4-org-alpha', true)` + `service.findMany()` → **2 rânduri** returnate
- **`v=norls`** — `SET LOCAL ROLE lab_booking_user` + `service.findMany()` (fără `set_config`) → **0 rânduri** (RLS cu GUC gol nu filtrează dar evaluează politica)

Test: autocannon 200 conexiuni × 10s, precedat de warm-up.

> **Notă metodologică:** Aceasta nu este o comparație RLS-ON vs RLS-OFF — ambele variante au politica activă. Diferența măsoară: costul apelului `set_config()` + returnarea 2 rânduri față de 0 rânduri. O comparație adevărată RLS-ON vs RLS-OFF ar necesita un rol cu atribut `BYPASSRLS`.

### Rezultate

| Metrică | `v=rls` (set_config + 2 rows) | `v=norls` (no set_config + 0 rows) | Diferență |
|---|---|---|---|
| req/s | 603 | 952 | +349 fără set_config |
| p50 | **192 ms** | **168 ms** | **+24 ms** (overhead set_config + serializare 2 rânduri) |
| p97.5 | 2127 ms | 798 ms | +1329 ms |
| p99 | 2397 ms | 1002 ms | — |
| max | 3740 ms | 1100 ms | — |
| Erori | 1311 (21.8%) | 6823 (71.6%) | |
| Cereri totale | 6028 | 9524 | **Total: 15,552** |

### Interpretare erori

Ambele variante folosesc același pool `lab_runtime` (max:1 per instanță). Variantele au erori EMAXCONNSESSION din cauza benchmark-ului anterior (200 conexiuni × 20s = saturare pool Supavisor). Rata de erori nu reflectă un comportament de producție — endpoint-ul de bench nu este proiectat pentru sarcini de tip load test.

### Overhead estimat

**~24 ms la p50** între varianta cu `set_config` (2 rânduri returnate) și fără `set_config` (0 rânduri). Această diferență include:
1. Costul apelului `set_config('app.organization_id', 'e4-org-alpha', true)` la Postgres (~1 ms)
2. Serializarea și transferul a 2 rânduri de servicii vs 0 rânduri (~5-10 ms)
3. Diferența în evaluarea politicii RLS (2 rânduri vizitate vs 0 pentru tabelul de 3 rânduri — neglijabil)

**Concluzie overhead:** `set_config(local=true)` adaugă overhead neglijabil (~24 ms total la p50 inclusiv data transfer). Mecanismul C rămâne viabil din perspectiva performanței.
