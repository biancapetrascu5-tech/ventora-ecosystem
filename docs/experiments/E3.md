# E3 — Izolare Postgres prin roluri

**Data:** 2026-10-24  
**Stare:** PASS  
**Prisma:** 7.10.1 | **Postgres:** 17 (Docker local)

## Întrebare

Poate Postgres să aplice izolarea între module la nivel de rol, astfel încât codul unui modul să nu poată accesa datele altui modul chiar dacă încearcă?

## Setup

3 roluri create prin `setup-db.sql` (idempotent):

| Rol               | Grant exclusiv pe         | Poate accesa          |
|-------------------|---------------------------|-----------------------|
| lab_core_user     | USAGE + ALL pe lab_core   | Doar lab_core.*       |
| lab_booking_user  | USAGE + ALL pe lab_booking| Doar lab_booking.*    |
| lab_crm_user      | USAGE + ALL pe lab_crm    | Doar lab_crm.*        |

`ALTER DEFAULT PRIVILEGES` asigură că tabelele create de superuser sunt accesibile rolului propriu,
inclusiv după un `migrate reset` (permisiunile se aplică automat tabelelor noi create de același utilizator).

## Concluzie

**DA** — rolurile Postgres oferă izolare reală la nivel de bază de date.
Chiar dacă codul aplicației încearcă `SELECT * FROM lab_crm.contacts`, Postgres refuză cu 42501.

Proba de control (E3-6…E3-9) confirmă că izolarea este **selectivă**, nu o blocare totală:
`lab_booking_user` are acces complet DML pe `lab_booking.*` și zero acces pe schemele altor module.

Aceasta este o apărare în profunzime față de izolarea prin tipuri (Prisma) sau prin cod (wrapper).

**Recomandare:** folosit ca strat suplimentar, nu ca unic mecanism de izolare.
La producție (Supabase), rolurile se configurează în `supabase/migrations/` ca SQL idempotent.
