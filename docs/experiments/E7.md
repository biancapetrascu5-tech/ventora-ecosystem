# E7 — Contract sincron CRM + Outbox + Inngest (dev server local)

**Data:** 2026-10-24  
**Stare:** PASS  
**Bază:** E4 (mecanismul C, Supabase staging), E8 (Inngest@4.26.0, inngest-cli@1.49.0)

## Întrebare

1. **Contract sincron**: Booking poate valida un contact prin CRM — ce se întâmplă când CRM-ul nu e activat sau contactul aparține altei organizații?
2. **Outbox → Inngest**: evenimentul `lab-booking.appointment.created.v1` ajunge la consumatorul CRM cu garantii de livrare?
3. **Idempotență**: aceeași livrare de două ori produce efectul o singură dată?
4. **Dead-letter**: un consumator care eșuează de 3 ori devine vizibil?
5. **Întârziere**: cât durează outbox → consumator?

---

## Arhitectura E7

```
Booking POST /api/e7/booking/create
  │
  ├── 1. validateContact(orgId, contactId)  ← contract sincron CRM
  │         ↓ ok | AppNotEnabled | CrossOrgContact
  │
  ├── 2. TX: appointment + outbox_event (atomic)
  │         set_config('app.organization_id', orgId, true)
  │
  └── 3. inngest.send() best-effort (outbox garantează persistența)

Inngest dev server (local, port 8288)
  └── crmAppointmentHandler (retries: 2)
        ├── step: mark outbox processedAt
        └── step: sync-to-crm (citire contact din CRM)
```

## Rezultate — Dispecer outbox (relay)

Script: `labs/experiments/e7-outbox-relay.mjs`  
Testează scenariul: Inngest oprit la booking → eveniment rămâne în outbox nelivrat → Inngest pornit → relay → consumator procesează o singură dată.

### Mecanismul relay

```typescript
async function relayPendingEvents() {
  // Citește evenimentele cu processedAt IS NULL
  const rows = await db.query(`
    SELECT id, "eventType", payload FROM lab_booking.outbox_events
    WHERE "processedAt" IS NULL ORDER BY "createdAt" ASC
  `);
  for (const row of rows) {
    await inngest.send({ id: row.id, name: row.eventType, data: row.payload });
    // processedAt NU e marcat de relay — consumatorul îl marchează după procesare
    // Dacă relay rulează din nou înainte ca consumatorul să termine → Inngest deduplică via id
  }
}
```

**Garanția idempotentă:** `outboxEventId` = Inngest event-id → a doua trimitere cu același id e ignorată de dev server. Consumatorul marchează `processedAt`, deci relay-ul ulterior nu mai include evenimentul în query.

### Rezultate

| Pas | Descriere | Rezultat |
|---|---|---|
| 1 | Eveniment inserat în outbox fără `inngest.send()` | `processedAt=NULL, attempts=0` |
| 2 | `relayPendingEvents()` rulat | `pending=1, sent=1` |
| 3 | Consumatorul CRM procesează | `processedAt` setat în DB |
| 4 | Al doilea relay | `pending=0`, consumator apelat de 1 dată total |

**Timp în outbox (creare → processedAt):** 697ms

✓ Relay livrează o singură dată chiar dacă rulează de mai multe ori.

## Observații tehnice

### RLS pe `lab_booking.appointments`
Inserarea programărilor necesită `set_config('app.organization_id', orgId, true)` în tranzacție — altfel WITH CHECK policy blochează INSERTul (42501). Acesta este aceeași gardă ca în E5/E6.

### `inngest.send()` best-effort pe Vercel
Pe Vercel fără dev server local, `inngest.send()` eșuează (nicio cheie cloud). Appointment + outbox sunt deja comise în DB — `inngestError` e returnat în răspuns, nu aruncă 500. În producție, un poller/cron citește outbox-ul și retrimite.

### Outbox garantează persistența
Chiar dacă `inngest.send()` eșuează, evenimentul stă în `outbox_events` cu `processedAt = null`. Un poller poate oricând relua livrarea.
