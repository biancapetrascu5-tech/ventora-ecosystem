# E2 — Migrații independente per modul

**Data:** 2026-10-24  
**Stare:** PASS  
**Prisma:** 7.10.1 | **Postgres:** 17 (Docker local)

## Întrebare

Poate fiecare modul să-și administreze propriile migrații, independent, fără ca un modul să afecteze schema altui modul?

## Versiunea Postgres — justificare

**Postgres 17.11** — ales pentru că Supabase folosește Postgres 17.11 pe instanța de staging (confirmat în dashboard: PostgreSQL 17.11, eu-central-1 Frankfurt). Aceasta elimină o variabilă de comportament la migrare.
Experimentul rulează pe aceeași versiune majoră ca staging-ul cloud, eliminând o variabilă de comportament la migrare.

## Setup

- 3 module: `lab_core` (6 modele), `lab_booking` (2 modele), `lab_crm` (1 model)
- Fiecare modul: `schema.prisma` propriu + `prisma.config.ts` cu URL de superuser
- URL de migrație: `postgresql://postgres:…@localhost:5432/ventora_labs?schema=<modul>`

## Constatare cheie: Prisma 7 — `url` scos din `schema.prisma`

Prisma 7.10.1 nu mai acceptă `url` în blocul `datasource` din fișierul `.prisma`.
URL-ul de conexiune se configurează acum în `prisma.config.ts`:

```ts
// labs/lab-core/prisma.config.ts
import { defineConfig } from 'prisma/config';
export default defineConfig({
  schema: './prisma/schema.prisma',
  datasource: { url: process.env.DATABASE_URL_SUPERUSER + '?schema=lab_core' },
});
```

**Impact arhitectural:** fiecare modul necesită un fișier `prisma.config.ts` separat.
Asta crește numărul de fișiere de configurare dar menține separarea clară per modul.

## Aplicarea migrațiilor (ordine directă)

Cele 3 module au migrații independente, aplicate separat:

```sh
# Modul 1 — lab_core (6 tabele)
DATABASE_URL_SUPERUSER=postgresql://postgres:localpass@localhost:5432/ventora_labs \
  prisma migrate dev --config lab-core/prisma.config.ts --name init

# Modul 2 — lab_booking (2 tabele)
DATABASE_URL_SUPERUSER=postgresql://postgres:localpass@localhost:5432/ventora_labs \
  prisma migrate dev --config lab-booking/prisma.config.ts --name init

# Modul 3 — lab_crm (1 tabel)
DATABASE_URL_SUPERUSER=postgresql://postgres:localpass@localhost:5432/ventora_labs \
  prisma migrate dev --config lab-crm/prisma.config.ts --name init
```

Fiecare comandă scrie exclusiv în propria schemă (`lab_core`, `lab_booking`, `lab_crm`).

## Verificare: migrații în ordine inversă și recreare pe bază curată

`prisma migrate reset` șterge toate tabelele din schemă și reaplică migrațiile de la zero.
A fost rulat pe `lab_crm` pentru a demonstra recrearea completă:

```sh
DATABASE_URL_SUPERUSER=postgresql://postgres:localpass@localhost:5432/ventora_labs \
  prisma migrate reset --config lab-crm/prisma.config.ts --force
```

Output real (rulare 2026-10-24):

```
Loaded Prisma config from lab-crm\prisma.config.ts.
Prisma schema loaded from lab-crm\prisma\schema.prisma.
Datasource "db": PostgreSQL database "ventora_labs", schema "lab_crm" at "localhost:5432"

Applying migration `20261024155410_init`

Database reset successful

The following migration(s) have been applied:

migrations/
  └─ 20261024155410_init/
    └─ migration.sql
```

Comportament confirmat:
1. Prisma șterge tabelele din `lab_crm` (în ordine inversă față de dependențele FK)
2. Recreează schema aplicând fiecare migrație în ordine cronologică
3. Schemele `lab_core` și `lab_booking` nu sunt atinse

**Notă Prisma 7:** `migrate reset` detectează contextul AI și blochează execuția fără consimțămînt explicit.
Aceasta este o funcție de securitate intenționată — la producție, `migrate reset` nu trebuie rulat automat.

## Concluzie

**DA** — migrațiile independente per modul funcționează corect cu Prisma 7.
Fiecare modul are `_prisma_migrations` exclusiv în propria schemă Postgres.
O migrație greșită pe un modul nu poate atinge tabelele altui modul.

`migrate reset` confirmat: Postgres 17 reaplică migrațiile în ordine cronologică pe o bază curată,
fără să afecteze schemele celorlalte module.

Overhead: 3 comenzi `migrate dev` în loc de 1, fiecare cu propriul `--config`.
Acceptabil pentru izolarea pe care o oferă.
