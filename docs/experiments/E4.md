# E4 — Prisma multi-client pe Vercel (runda B)

**Data:** 2026-10-24  
**Stare:** PASS  
**Prisma:** 7.10.1 | **Next.js:** 16.4.3 Turbopack | **Node.js runtime:** nodejs24.x | **Regiune:** fra1

## Întrebare

Cum se comportă arhitectura cu mai mulți clienți Prisma (câte unul per modul/rol) pe un serverless deployment Vercel cu conexiune la Supabase staging?  
Care variantă oferă cel mai bun echilibru între izolarea la nivel de bază de date și eficiența conexiunilor?

## Rezultate load test

### Metodă

- Unealtă: autocannon, 200 conexiuni concurente, 10 secunde per rulare
- Monitor: `pg_stat_activity` interogat la fiecare secundă (prin `DATABASE_URL_SUPERUSER`)
- Warm-up: 1 cerere solitară înainte de fiecare rulare
- Pauză: 60 secunde între A și B (conexiunile session pooler se eliberează greu)

### A-combined (`/api/a/combined`)

Folosește **2 clienți Prisma** (`lab_core_user` + `lab_booking_user`), 3 query-uri paralele: `organizations`, `services`, `appointments`. Pooler: session (5432).

| Metrică | Valoare |
|---|---|
| Cold start (prima cerere) | **1087 ms** |
| Latență warm (warm-up 2) | 279 ms |
| req/s (medie) | **619** |
| Latență p50 | 211 ms |
| Latență p97.5 | 1661 ms |
| Latență p99 | 1798 ms |
| Latență max | 2346 ms |
| Erori timeout | 0 |
| Erori non-2xx | **294** (4.7%) |
| Cereri totale | 6194 |
| Conexiuni DB peak | `lab_core_user`=16 · `lab_booking_user`=16 · **total=32** |

**Cauza celor 294 erori:** Supavisor menține un pool separat per rol (confirmat în documentația Supabase: *„Pool size is the maximum number of direct connections the pooler can keep per unique user, database, and mode combination."*). La cold start, 200 conexiuni HTTP concurente generează rapid cereri noi de conectare per rol. Când pool-ul per rol se saturează, Supavisor returnează `EMAXCONNSESSION` — clienții care depășesc capacitatea primesc eroare în loc să fie puși la coadă (comportament transaction mode diferit față de session mode). Codul de eroare PostgreSQL: **`53300` (too_many_connections)**.

La scale (15 module), fiecare request ar conține 15 tranzacții secvențiale — overhead crește liniar.

Verificat manual la `isolationOk: true`:

| Verificare | Rezultat |
|---|---|
| `connectRole` | `lab_runtime` |
| `bookingRoleInsideTx` (SET LOCAL ROLE) | `lab_booking_user` ✓ |

| `setLocalRoleRevertsCorrectly` (rol după COMMIT) | `true` ✓ — `lab_runtime` |

## Conexiuni DB — analiză

### Supavisor: pool separat per rol

**Confirmat prin documentația Supabase:** Supavisor ține un pool separat per combinație `(user, database, mode)`. La session pooler, fiecare conexiune client ține o conexiune server pentru toată durata sesiunii clientului.

La load (200 conexiuni HTTP → ~16 instanțe de funcție Vercel active simultan):

| Variant | Conexiuni DB per instanță | Conexiuni DB totale (16 inst.) | La 15 module |
|---|---|---|---|
| A — session pooler | 2 roluri × 1 = 2 | 16 × 2 = **32** | 16 × 15 = **240** ⚠️ |
| B — session pooler | 1 rol × 1 = 1 | 16 × 1 = **16** | 16 × 1 = **16** |
| C — transaction pooler | 1 rol × 1 = 1 (secvențial) | ≤ 16 × 1 = **16** | ≤ 16 × 1 = **16** |

**Limita instanței:** Supabase staging pe t3.micro permite **60 conexiuni directe** (nu 200 — 200 este limita pooler-ului Supavisor per default). La 15 module active simultan cu Variant A + session pooler, `16 × 15 = 240` conexiuni directe → **depășire de 4× față de limita DB**.

**De ce A are 294 erori și B zero:** Cu session pooler, pool-ul per rol are un `pool_size` fix. La burst de 200 conexiuni HTTP la cold start, pool-ul pentru fiecare rol (core_user, booking_user) se saturează rapid. Supavisor retrimite `EMAXCONNSESSION` la noile cereri care depășesc `pool_size`. B folosește un singur rol cu un singur pool — cererile în exces sunt puse la coadă (latență mare) în loc să fie respinse.

## Proiecție la 15 module

### Variant A + session pooler
- 16 instanțe × 15 roluri = **240 conexiuni** → depășire de 4× (limita DB: 60)
- Erorile EMAXCONNSESSION se vor amplifica proporțional cu numărul de roluri

### Variant A + transaction pooler
- Conexiunile se eliberează după fiecare query → nu se acumulează
- Risc depășire eliminat
- Latența crește față de session pooler (BEGIN/COMMIT overhead per query)
- Izolarea se păstrează, dar `Promise.all` pe 2 clienți concurenți = 2 conexiuni simultane per request → la 15 module, 15 conexiuni simultane per funcție → la 16 funcții = 240 conexiuni ⚠️

### Variant B (orice pooler)
- 16 conexiuni indiferent de numărul de module
- Fără risc pooler
- **Izolarea între module dispare complet la nivel DB**

### Variant C + transaction pooler
- Tranzacții secvențiale — 1 conexiune la un moment dat per funcție
- La 15 module: 15 tranzacții secvențiale per request — conexiuni peak = 16 (nu 16 × 15)
- Izolarea se păstrează
- Overhead throughput creşte liniar cu numărul de module (~23% față de B la 2 module/request)

## Recomandare D-DB-1

**Decizie: Variant C — `lab_runtime` NOINHERIT + `SET LOCAL ROLE` per tranzacție + transaction pooler**

### Argumente

**Pentru C:**

1. **Singura variantă cu izolare DB și conexiuni controlate simultan.** A are izolare dar conexiuni care scapă de sub control la scale (240 direct la 15 module). B are conexiuni eficiente dar pierde izolarea DB. C rezolvă ambele probleme: un singur pool, iar SET LOCAL ROLE asigură că fiecare query rulează cu rolul corect.

2. **Zero erori sub sarcină.** Spre deosebire de A (4.7% EMAXCONNSESSION), C nu depășește niciodată pool_size-ul Supavisor — un singur rol în pool, conexiunile se eliberează după fiecare tranzacție.

3. **Scalabilitate liniară în conexiuni.** La 15 module, C folosește 16 conexiuni (independent de N module). A necesita 16 × N = 240. Transaction pooler amplifică avantajul la scale.

4. **Izolarea E3 verificată prin test explicit.** `SET LOCAL ROLE` revine corect la `lab_runtime` după tranzacție — o cerere ulterioară fără SET ROLE nu moștenește permisiunile modulului (NOINHERIT confirmat).

**Concesie față de A și B:**

- Throughput inferior: 277 req/s vs 619 (A) și 359 (B). Overhead: 2 tranzacții secvențiale în loc de queries paralele + transaction pooler per-tranzacție. La scale, acest overhead crește liniar cu numărul de module per request.
- Mitigare posibilă: gruparea queries dintr-un singur modul într-o singură tranzacție (ceea ce C deja face) și minimizarea numărului de module per request HTTP.

**Împotriva lui B:**
- `lab_multi_user` are GRANT pe toate schemele — un query greșit dintr-un modul CRM poate returna date Core fără niciun refuz din Postgres.

**Împotriva lui A + session pooler:**
- 240 conexiuni directe la 15 module > 60 limita staging — overflow garantat.

**Împotriva lui A + transaction pooler:**
- `Promise.all` pe N clienți concurenți = N conexiuni simultane per funcție → la 15 module, același overflow ca session pooler.

### Acțiune recomandată

1. Migrează `DATABASE_URL_RUNTIME` ca singura variabilă de aplicație → **transaction pooler port 6543** (deja configurat).
2. Rolul `lab_runtime` (NOINHERIT) + GRANT la rolurile modulelor — deja în `setup-db-staging.sql`.
3. Fiecare request HTTP folosește `db.$transaction(async (tx) => { await tx.$executeRawUnsafe('SET LOCAL ROLE <modul>'); ... })` per modul accesat.
4. Rolurile individuale (`lab_core_user`, `lab_booking_user` etc.) rămân pentru migrări și accese directe de admin — nu intră în pooler-ul aplicației.
