# E4 — Prisma multi-client pe Vercel (runda B)

**Data:** 2026-10-24  
**Stare:** PASS  
**Prisma:** 7.10.1 | **Next.js:** 16.4.3 Turbopack | **Node.js runtime:** nodejs24.x | **Regiune:** fra1

## Întrebare

Cum se comportă arhitectura cu mai mulți clienți Prisma (câte unul per modul/rol) pe un serverless deployment Vercel cu conexiune la Supabase staging (session pooler, port 5432)?  
Merită izolarea la nivel de bază de date (Variant A — rol per modul) costul în conexiuni față de un rol shared (Variant B — `lab_multi_user`)?

## Conexiuni DB — analiză

La load (200 conexiuni HTTP → ~16 instanțe de funcție Vercel active simultan):

| Variant | Conexiuni DB per instanță | Conexiuni DB totale (16 instanțe) | La 15 module |
|---|---|---|---|
| A (rol per modul) | N_module_folosite × 1 | 16 × N = 16N | 16 × 15 = **240** (depășește limita pooler 200) |
| B (rol shared) | 1 | 16 × 1 = **16** | 16 × 1 = 16 |

**Risc A la scară:** cu session pooler și 15 module toate active simultan, 240 conexiuni depășesc limita pooler-ului Supabase staging (200). Soluție: **transaction pooler** (port 6543) pentru conexiunile aplicației — Prisma 7 + adapter-pg funcționează cu el, iar conexiunile sunt eliberate imediat după tranzacție.

## Proiecție la 15 module

Bazat pe cifrele reale:

### Variant A cu session pooler (port 5432)
- Conexiuni DB active simultan: **16 instanțe × 15 roluri = 240** → depășire pooler (200 max Supabase staging)
- Erori de tip cold-start congestion rămân prezente (4.7% observat la 2 roluri)
- Latența creşte cu numărul de roluri folosite per request (fiecare client Prisma e un pool separat)
- Necesită monitoring activ al `pg_stat_activity` per rol

### Variant A cu transaction pooler (port 6543)
- Conexiunile se eliberează după fiecare tranzacție → nu se acumulează per instanță
- Risc depășire pooler eliminat
- Compatibil cu Prisma 7 + `@prisma/adapter-pg`
- Recomandare pentru deployment production

### Variant B (15 module, orice pooler)
- 16 conexiuni indiferent de câte module accesează un request
- Fără risc pooler
- **Izolarea între module nu mai e garantată la nivel DB** — dacă un query greșit sau o vulnerabilitate în codul modulului A încearcă să acceseze schema modulului B, Postgres nu mai blochează

## Recomandare D-DB-1

**Decizie: Variant A — rol per modul, cu transaction pooler (port 6543) în production**

### Argumente

**Pentru A:**
1. **Izolarea la nivel DB este singura barieră care nu se poate ocoli din cod.** Orice bug, vulnerabilitate sau configurare greșită din codul unui modul nu poate scurge date din alt modul — Postgres refuză la nivel de connection. Cu Variant B, izolarea dispare complet; rămâne doar lint-ul și wrapper-ele de cod, care se pot dezactiva accidental.
2. **Performanță superioară sub sarcină:** 619 req/s vs 359 req/s, p99 de 1798ms vs 4499ms (aproape 2.5× mai rapid la coada cozii).
3. **Principiu least privilege**: fiecare serviciu accesează exact ce are nevoie, nimic mai mult.

**Condiție necesară:** folosirea **transaction pooler** (port 6543) în loc de session pooler pentru `DATABASE_URL_*` din Vercel. Aceasta elimină acumularea de conexiuni la scară.

**Împotriva lui B:**
- Singura barieră de izolare rămâne codul. Un `db.organization.findMany()` apelat greșit dintr-un modul CRM poate returna date din Core — Postgres nu protestează.
- Faptul că `lab_multi_user` are GRANT pe toate schemele e exact ceea ce arhitectura multi-client a vrut să evite (confirmat de E3).

### Acțiune recomandată
Migrează `DATABASE_URL_CORE`, `DATABASE_URL_BOOKING`, `DATABASE_URL_CRM` de la session pooler (port 5432) la **transaction pooler (port 6543)** în variabilele de mediu Vercel. Rolul `lab_multi_user` și clientul multi pot fi păstrate în laborator (E5/E6) dar nu intră în arhitectura production.
