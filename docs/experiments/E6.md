# E6 — Matrice garduri: RLS vs. application guard

**Data:** 2026-10-24  
**Stare:** PASS  
**Bază:** Mecanismul C din E4 + RLS din E5

## Întrebare

Pentru fiecare tip de acces posibil (SELECT fără filtru, SELECT cross-org, COUNT, raw SQL, org greșit, fără org), cine blochează accesul: RLS sau codul aplicației?  
Există cazuri în care RLS nu prinde, iar codul aplicației trebuie să compenseze?

---

## Setup

Același ca E5: RLS activ pe `lab_booking.services` și `lab_booking.appointments`.  
Helper per test:

```typescript
async function runWithOrg<T>(orgId: string, fn: (tx) => Promise<T>): Promise<T> {
  return db.$transaction(async (tx) => {
    await tx.$executeRawUnsafe('SET LOCAL ROLE lab_booking_user');
    await tx.$executeRaw`SELECT set_config('app.organization_id', ${orgId}, true)`;
    return fn(tx);
  });
}
```

---

## Rezultate — toate 7 cazuri

### E6-1: SELECT fără filtru explicit de org

```typescript
tx.service.findMany()  // fără WHERE
```

| | |
|---|---|
| RLS prins? | **DA** — filtrat la 2 rânduri (alpha), cross-org=false |
| App prins? | Nu (nu există guard la nivel de aplicație) |
| Concluzie | RLS este suficient: chiar și un query fără WHERE returnează doar datele org-ului curent |

### E6-2: SELECT cu filtru corect pe org

```typescript
tx.service.findMany({ where: { organizationId: 'e4-org-alpha' } })
```

| | |
|---|---|
| RLS prins? | Nu (cazul corect — 2 rânduri returnate, comportament așteptat) |
| App prins? | Nu |
| Concluzie | Accesul corect nu este blocat. RLS permite accesul când `set_config` și filtrul se potrivesc |

### E6-3: SELECT cross-org (filter pentru altă org)

```typescript
tx.service.findMany({ where: { organizationId: 'e4-org-beta' } })
// executat cu orgId='e4-org-alpha' în set_config
```

| | |
|---|---|
| RLS prins? | **DA** — 0 rânduri returnate (WHERE + RLS ambele aplicate, RLS câștigă) |
| App prins? | Nu |
| Concluzie | Un query care încearcă explicit altă org returnează 0 rânduri, nu eroare — RLS nu ridică excepție, silently filtrează |

### E6-4: COUNT(*) fără filtru

```typescript
tx.$queryRaw`SELECT COUNT(*) as count FROM lab_booking.services`
```

| | |
|---|---|
| Rezultat | COUNT = 2 (nu 3 — total servicii = 3: 2 alpha + 1 beta) |
| RLS prins? | **DA** — RLS se aplică înainte de agregare |
| App prins? | Nu |
| Concluzie | Agregările nu scapă de RLS. COUNT(*) fără WHERE reflectă vizibilitatea RLS, nu totalul fizic |

### E6-5: Raw SQL SELECT (ocolește Prisma model layer)

```typescript
tx.$queryRaw`SELECT id, "organizationId" FROM lab_booking.services`
```

| | |
|---|---|
| Rezultat | 2 rânduri, niciun cross-org |
| RLS prins? | **DA** — RLS se aplică la nivel Postgres, independent de cum vine query-ul |
| App prins? | Nu |
| Concluzie | RLS nu poate fi ocolit prin raw SQL. Politica se evaluează per-rând la executor, nu la parser |

### E6-6: Org-id greșit în context (eroare de apelant)

```typescript
runWithOrg('e4-org-beta', (tx) => tx.service.findMany())
// apelantul a transmis org greșit — e4-org-beta în loc de e4-org-alpha
```

| | |
|---|---|
| Rezultat | 1 rând returnat — serviciul lui beta |
| RLS prins? | Nu (din perspectiva RLS, este un query valid pentru org-beta) |
| App prins? | Nu |
| Concluzie | RLS nu poate detecta că apelantul a trecut org-ul greșit — responsabilitate aplicație. Codul trebuie să extragă orgId din token/sesiune autentificată, nu din input utilizator |

### E6-7: Fără org-id în context (`set_config` omis)

```typescript
db.$transaction(async (tx) => {
  await tx.$executeRawUnsafe('SET LOCAL ROLE lab_booking_user');
  // Nicio apelare set_config — app.organization_id = NULL sau ""
  return tx.service.findMany();
})
```

| | |
|---|---|
| Rezultat | 0 rânduri returnate |
| RLS prins? | **DA** — NULL/`""` nu se potrivește niciunui `organizationId` → 0 rânduri |
| App prins? | Nu |
| Concluzie | **Default securizat:** omiterea accidentală a `set_config` expune 0 rânduri, nu toate rândurile. Fail-safe corect |

---

## Rezumat matrice — citiri

| Caz | Tip atac/eroare | RLS prins | App prins | Blocat? |
|---|---|---|---|---|
| E6-1: SELECT fără filtru | Uitare WHERE | **DA** | Nu | ✓ securizat |
| E6-2: SELECT corect | Acces legitim | Nu (corect) | Nu | ✓ permis corect |
| E6-3: SELECT cross-org | Încercare acces altă org | **DA** | Nu | ✓ securizat |
| E6-4: COUNT(*) | Enumerare prin agregare | **DA** | Nu | ✓ securizat |
| E6-5: Raw SQL | Ocolire ORM | **DA** | Nu | ✓ securizat |
| E6-6: Org greșit | Eroare apelant | Nu | Nu | ⚠️ risc la aplicație |
| E6-7: Fără org-id | Omitere set_config | **DA** (0 rows) | Nu | ✓ fail-safe securizat |

**RLS prins: 5/7 — celelalte 2 nu sunt vulnerabilități, ci comportament corect (E6-2) și responsabilitate apelant (E6-6).**

## Scrieri — E6-8 la E6-12

Testele de scriere rulează în tranzacții care întotdeauna fac **rollback** (rollback deliberat după măsurare) pentru a nu modifica datele de test.

### E6-8: INSERT cu organizationId al altei organizații

```typescript
await tx.service.create({
  data: { id: '...', organizationId: 'e4-org-beta', name: 'CrossOrgHack', durationMinutes: 30 }
});
// org în context = 'e4-org-alpha' — WITH CHECK: 'e4-org-beta' ≠ 'e4-org-alpha' → 42501
```

| | |
|---|---|
| RLS prins? | **DA** — WITH CHECK (42501) a blocat INSERT cross-org |
| App prins? | Nu |
| Concluzie | `WITH CHECK` pe politica RLS blochează inserarea de rânduri cu `organizationId` diferit de cel din context |

### E6-9: UPDATE rândul altei organizații

```typescript
UPDATE lab_booking.services SET name = 'hacked' WHERE "organizationId" = 'e4-org-beta' RETURNING id
// org în context = 'e4-org-alpha' — USING: rândul beta invizibil → 0 rânduri actualizate
```

| | |
|---|---|
| Rezultat | 0 rânduri actualizate (rollback) |
| RLS prins? | **DA** — USING policy face rândul beta invizibil; UPDATE nu poate atinge ce nu vede |
| App prins? | Nu |
| Concluzie | UPDATE cross-org este **silențios** (0 rânduri, nu eroare) — codul trebuie să verifice `count > 0` |

### E6-10: DELETE rândul altei organizații

| | |
|---|---|
| Rezultat | 0 rânduri șterse (rollback) |
| RLS prins? | **DA** — USING policy, 0 rânduri vizibile pentru orgId beta |
| App prins? | Nu |
| Concluzie | Identic cu UPDATE — silențios; necesită verificare `count > 0` la nivel de cod |

### E6-11: updateMany fără filtru org (Prisma)

```typescript
tx.service.updateMany({ data: { name: 'touched' } })
// Fără WHERE — RLS USING limitează la rândurile org-ului curent (alpha = 2)
```

| | |
|---|---|
| Rezultat | 2 rânduri actualizate (nu 3 — total fizic; rollback) |
| RLS prins? | **DA** — RLS limitează updateMany la rândurile org-ului din context |
| App prins? | Nu |
| Concluzie | `updateMany` fără filtru nu șterge tot — RLS limitează la org curentă. Dar ATENȚIE: **tot modifică datele org-ului curent** — necesită validare explicită la nivel de aplicație |

### E6-12: deleteMany fără filtru (Prisma)

```typescript
tx.service.deleteMany({})
// Fără WHERE — RLS USING limitează la rândurile org-ului curent
```

| | |
|---|---|
| Rezultat | 2 rânduri șterse (nu 3; rollback) |
| RLS prins? | **DA** — RLS limitează deleteMany la rândurile org-ului curent |
| App prins? | Nu |
| Concluzie | `deleteMany({})` cu RLS = „șterge tot al meu", nu „șterge tot din tabel". Totuși **este distructiv** pentru org curentă — necesită guard explicit în cod |

### Rezumat matrice — scrieri

| Caz | Tip operație | RLS prins | App prins | Blocat? |
|---|---|---|---|---|
| E6-8: INSERT cross-org | Scriere cu orgId greșit | **DA** (42501 WITH CHECK) | Nu | ✓ eroare |
| E6-9: UPDATE cross-org | Modificare rând altă org | **DA** (0 rânduri, USING) | Nu | ✓ silențios |
| E6-10: DELETE cross-org | Ștergere rând altă org | **DA** (0 rânduri, USING) | Nu | ✓ silențios |
| E6-11: updateMany fără filtru | Editare masivă | **DA** (limitează la org curentă) | Nu | ⚠️ parțial |
| E6-12: deleteMany fără filtru | Ștergere masivă | **DA** (limitează la org curentă) | Nu | ⚠️ parțial |

**RLS prins toate 5/5 scrieri.**

> **Notă E6-11/E6-12:** „prins de RLS" înseamnă că RLS a limitat operația la org curentă. Totuși, un `updateMany`/`deleteMany` fără filtru explicit rămâne distructiv pentru datele org curentă — codul aplicației trebuie să impună filtre sau să ceară confirmare explicită.

## Analiza cazului E6-6 — singura lacună acționabilă

RLS nu poate valida că orgId transmis de apelant corespunde organizației autentificate.  
Mecanism de mitigare obligatoriu la nivel de aplicație:

1. **Nu accepta `orgId` din request params / body** — extrage-l din JWT/sesiune validată
2. **Verificare înainte de `runWithOrg`:** `assert(session.orgId === requestedOrgId)`
3. **Middleware de autorizare** care validează că utilizatorul aparține organizației pentru care face request

Aceste verificări **nu înlocuiesc** RLS — sunt un al doilea strat de apărare (defense-in-depth).

---

## Concluzie

RLS cu mecanismul C (`SET LOCAL ROLE` + `set_config(local=true)`) oferă un **nivel de protecție puternic și consistent** pentru toate scenariile de citire:
- Se aplică la Prisma ORM, la `$queryRaw`, la COUNT, la subqueries
- Default securizat: dacă `set_config` e omis accidental, 0 rânduri sunt expuse
- Nu poate fi ocolit de codul aplicației (se aplică la executor Postgres, sub orice layer)

Singura lacună este **corectitudinea orgId-ului** — care necesită validare la nivel de autentificare/autorizare în aplicație.
