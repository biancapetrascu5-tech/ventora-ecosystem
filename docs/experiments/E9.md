# E9 — Better Auth 1.7.12: sesiuni, organizații, 2FA

**Data:** 2026-10-25  
**Stare:** PASS  
**Bază:** E4 (labs/e4-vercel), Supabase staging (lab_core), Vercel fra1

## Întrebare

Poate Better Auth 1.7.12 servi drept strat de autentificare pentru Ventora Hub cu:
- autentificare headless (bearer token, fără cookie sesiune pe client)?
- sesiuni de organizație cu rol imediat consistent (fără cache vechi)?
- 2FA TOTP cu backup codes single-use?
- protecție împotriva injectării de `organizationId` din request?

| Parametru | Valoare |
|-----------|---------|
| Pachet | `better-auth@1.7.12` |

| Parole | scrypt (implicit Better Auth) |
| `basePath` | `/api/e9/auth` |
| `cookieCache` | dezactivat (`{ enabled: false }`) |
| `rateLimit` | dezactivat (`{ enabled: false }`) pentru teste |

**Observație critică — `basePath`:** Better Auth citește `basePath`-ul din prima cerere primită pentru a construi URL-urile interne. Dacă ruta Next.js nu este la calea implicită `/api/auth`, `basePath` trebuie declarat explicit în `betterAuth()`; altfel fiecare cerere returnează 500 cu "Could not get base URL from request".

| Aserțiune | Rezultat |
|-----------|---------|
| T1.1 signup 200 | PASS |

Better Auth returnează token-ul de sesiune în header-ul `set-auth-token` la sign-in. Clientul îl trimite ulterior ca `Authorization: Bearer <token>`. Pluginul `bearer()` activează acest comportament; fără el, autentificarea headless nu funcționează.

### T2 — Retrogradare rol (admin → member), efect imediat (6/6 PASS)

| Aserțiune | Rezultat |
|-----------|---------|
| T2.0 create-org (owner automat) | PASS |
| T2.1 add-member ca admin | PASS |
| T2.2 set-active-org | PASS |
| T2.3 activeOrganizationId setat în sesiune | PASS |
| T2.4 owner retrogradează admin → member | PASS |
| T2.5 sesiune accesibilă după retrogradare | PASS |

`cookieCache: { enabled: false }` garantează că `getSession` citește din baza de date la fiecare cerere. Modificarea rolului de către owner are efect imediat la cererea următoare cu aceeași sesiune, fără re-login.

**Constrângere Better Auth:** Numai `owner` poate retrograda un `admin`. Un `admin` nu se poate retrograda singur și nu poate retrograda alt `admin`. Testul creează un owner separat cu `createOrganization` (owner automat) și îl folosește pentru retrogradare.

### T4 — 2FA TOTP + backup codes (8/8 PASS)

| Aserțiune | Rezultat |
|-----------|---------|
| T4.1 enable-2fa 200 | PASS |
| T4.2 totpURI prezent | PASS |
| T4.3 backupCodes prezente (10 coduri) | PASS |
| T4.3b verify-totp activează 2FA | PASS |
| T4.4 backup code valid la prima folosire | PASS |
| T4.5 backup code invalid la refolosire (single-use) | PASS |
| T4.6 regenerare backup codes 200 | PASS |
| T4.7 coduri noi diferite de cele vechi | PASS |

**Detaliu implementare:** `enable` creează secretul TOTP și backup codes dar NU setează `user.twoFactorEnabled = true` până la prima verificare TOTP reușită. `generate-backup-codes` verifică `twoFactorEnabled` și aruncă `BAD_REQUEST` dacă nu este setat. Ordinea corectă: `enable` → `verify-totp` (activare) → `generate-backup-codes`.

La activarea 2FA prin `verify-totp`, sesiunea veche este înlocuită. Bearer plugin-ul returnează noul token în header-ul `set-auth-token`.

## Concluzii

Better Auth 1.7.12 **îndeplinește cerințele D-AUTH-2** pentru Ventora Hub:

1. **Bearer token headless** funcționează prin pluginul `bearer()`. Token-ul este un token de sesiune opac (nu JWT), valid până la revocare sau expirare.
2. **Organizații cu sesiune** — `organization()` plugin stochează `activeOrganizationId` în sesiune; cu `cookieCache: false`, modificările de rol sunt imediat vizibile.
3. **2FA TOTP** funcționează cu backup codes single-use și regenerare. Fluxul de activare înlocuiește sesiunea (comportament intenționat de securitate).
4. **Injecție organizationId** este blocată by design — sesiunea nu citește `organizationId` din request.

### Observații pentru producție

- **`rateLimit`** trebuie RE-ACTIVAT în producție (`rateLimit: { enabled: true }`). A fost dezactivat numai pentru a permite multiple sign-in-uri rapide în teste. **Notă Pasul 0.4:** înainte de merge în producție, adaugă un test explicit care verifică că rate limiting-ul blochează >N cereri consecutive de sign-in de la același IP (fereastra implicită Better Auth: 10 req/10s pentru `/sign-in/*`).
- **`cookieCache`** dezactivat crește numărul de query-uri DB. La latența p50=7ms și volumul actual, este acceptabil. Dacă apare presiune pe conexiuni, se poate activa cache-ul cu TTL scurt (30–60s) și se testează revocarea cu T3.
- **Schema `ba_*`** trebuie migrată explicit înainte de deploy (nu există auto-migrate). Fișierul `e9-migrate-staging.mjs` este idempotent.
- **`basePath`** este obligatoriu dacă ruta nu este la `/api/auth`.
