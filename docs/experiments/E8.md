# E8 — Cote cu rezervare (quota reservation system)

**Data:** 2026-10-24  
**Stare:** PASS  
**Bază:** E4 (mecanismul C), Supabase staging, Vercel fra1

## Întrebare

Un sistem de limite (ex: 10 programări per lună) trebuie să reziste la cereri paralele fără supra-alocare.  
Poate un pattern `rezervare → confirmare → eliberare` cu `UPDATE...RETURNING` atomic să garanteze că exacte `N` cereri reușesc dintr-un volum mai mare?  
Ce se întâmplă dacă procesul moare între rezervare și confirmare?

## Mecanism

### 1. Rezervare atomică

```sql
UPDATE lab_core.usage_counters
SET reserved = reserved + $amount, "updatedAt" = NOW()
WHERE "organizationId" = $orgId
  AND metric = $metric
  AND count + reserved + $amount <= "limit"
RETURNING id, count, reserved, "limit"
```

Dacă UPDATE returnează 0 rânduri → cota ar fi depășită → 409 Quota Exceeded.  
Dacă returnează un rând → rezervarea s-a efectuat atomic; INSERT în `quota_reservations` în aceeași tranzacție.

### 2. Confirmare

`confirm`: `reserved -= amount`, `count += amount` — mută consumul din "rezervat" în "confirmat".

### 3. Eliberare

`release`: `reserved -= amount` — anulează rezervarea fără să crească `count`.

### 4. Reconciliere (crash recovery)

`reconcile`: găsește rezervările cu `status = 'reserved' AND expiresAt < NOW()`, le marchează `expired` și reduce `reserved` pe contor.

### 5. Idempotență

Dacă `operationId` există deja cu status `reserved` sau `confirmed`, `reserve` returnează același rezultat fără a dubla consumul.

## Rezultate

### Test 1: ciclu complet rezervare → confirmare → eliberare

```
RESERVE  → ok, reserved=1, count=0, ms=230
CONFIRM  → ok, reserved=0, count=1
RESERVE  → ok, reserved=1, count=1, ms=43
RELEASE  → ok, reserved=0, count=1 (stabil)
```

| Pas | Rezultat | count | reserved |
|---|---|---|---|
| initial (setup) | — | 0 | 0 |
| reserve(amount=1) | ok | 0 | 1 |
| confirm | ok | 1 | 0 |
| reserve(amount=1) | ok | 1 | 1 |
| release | ok | 1 | 0 |

✓ Ciclul complet funcționează corect.

---

### Test 2: 50 cereri paralele, cotă=10

```
n=50, quotaLimit=10
succeeded: 10  ← exact limita
failed:    40
exactlyLimitSucceeded: true
counterAfter: { count: 0, reserved: 10, limit: 10 }
```

✓ **Exact 10 reușesc** dintr-un total de 50 cereri paralele. RNG-ul nu contează — atomicitatea `UPDATE...RETURNING` garantează că exact `limit - (count + reserved)` slot-uri sunt disponibile.

---

### Test 3: reconciliere după crash simulat

```
RESERVE(amount=2, ttlSeconds=1) → ok, reserved=2
[așteptare 3s — procesul s-ar fi oprit între rezervare și confirmare]
STATUS → count=1, reserved=2
RECONCILE → { reconciled: 1 }
STATUS → count=1, reserved=0
```

✓ Reconcilierea a găsit rezervarea expirată și a eliberat `reserved` corect. Contor stabil.

---

### Test 4: idempotență (același operationId de 2 ori)

```
RESERVE(operationId="test-op-1") → ok, reservationId=X, reserved=1
RESERVE(operationId="test-op-1") → ok, idempotent=true, reservationId=X, ms=4
STATUS → reserved rămâne 1 (nu 2)
```

✓ A doua cerere cu același `operationId` returnează același rezultat fără să dubleze rezervarea. Latența idempotentă: 4ms (vs 230ms prima cerere — fără accesul DB UPDATE).

---

### Test 5: latența rezervării (p50/p95)

| Percentilă | Latență |
|---|---|
| p50 | **250 ms** |
| p95 | **280 ms** |

Latența include: cold start parțial Vercel + round-trip fra1 → Supabase Frankfurt + UPDATE atomic + INSERT rezervare în aceeași tranzacție.  
Idempotent (hit lookup only): **4 ms** — fără UPDATE.
